You are a principal .NET architect, security engineer, desktop UX designer,

and senior C# developer.



Your task is to research and produce a complete, implementation-ready

architecture and development plan for a professional file-management,

file-transfer, and synchronization application named:



&#x20;   StorageHUB



Do not write production code yet.



The first response must be a researched technical design and phased

implementation plan. Do not scaffold projects or generate placeholder

classes until the design has been reviewed and approved.



============================================================

1\. PRODUCT VISION

============================================================



StorageHUB should be a modern, reliable, security-focused alternative to

FileZilla, WinSCP, traditional dual-pane file managers, and basic cloud

storage clients.



It should combine:



\- A powerful local file explorer

\- A dual-pane local/remote and remote/remote file manager

\- A connection manager

\- A persistent transfer queue

\- S3-compatible object-storage browsing

\- FTP and FTPS

\- SFTP

\- Manual and scheduled synchronization

\- A background synchronization service

\- Secure, centrally managed credentials

\- Extensible storage-provider plugins

\- Detailed settings, logging, health, and diagnostics



The primary platform is Windows.



Technology requirements:



\- C#

\- .NET 10

\- Windows Forms for the initial desktop UI

\- CodeLogic 4 as the application framework

\- CodeLogic NuGet libraries wherever they are appropriate

\- Architecture must permit a separate Linux-compatible UI later

\- The non-UI core and sync service should remain platform-neutral wherever

&#x20; technically possible



Do not claim that WinForms itself will run on Linux. Keep the WinForms

project isolated from the application core so that a future Avalonia,

GTK, Uno, or other Linux-capable frontend can reuse the core.

\- Upload

\- Download

\- Copy

\- Move

\- Delete

\- Rename

\- Directory creation

\- Recursive operations

\- Remote-to-remote relay

\- Resumable transfers where supported

\- Transfer verification

\- Pause

\- Resume

\- Cancel

\- Per-job priority

\- Per-provider concurrency

\- Bandwidth limits

\- Progress

\- Speed

\- ETA

\- Temporary-name upload followed by atomic rename where supported

\- Partial-file cleanup policy

\- Disk-space checks

\- Network-offline handling

\- Application-restart recovery

\- Background execution

For remote-to-remote transfers:



1\. Prefer a provider-native operation when both endpoints support it.

2\. Otherwise relay through a bounded streaming pipeline.

3\. Do not buffer the whole file.

4\. Support cancellation and progress.

5\. Document security and temporary-disk implications.



Create a transfer-job state machine containing states such as:



\- Pending

\- Preparing

\- Connecting

\- Transferring

\- Verifying

\- Finalizing

\- Paused

\- Retrying

\- Completed

\- Failed

\- Cancelled



Improve these states where necessary.



Design persistent recovery so interrupted transfers can be reloaded after

an application or machine restart without falsely claiming they can resume

when the provider lacks that capability.

20\. ACCEPTANCE CRITERIA

============================================================



At minimum, the finished design must make these scenarios possible:



1\. A user creates an SFTP connection with an encrypted SSH private key.

2\. The private-key passphrase is saved securely outside JSON and SQLite.

3\. The user browses local files on the left and SFTP on the right.

4\. The user drags a 20 GB file to the remote pane.

5\. The UI remains responsive and shows progress.

6\. The transfer can be cancelled and retried.

7\. The SSH host fingerprint is validated.

8\. A user creates an explicit FTPS connection with a PFX client certificate.

9\. The PFX password comes from the central credential vault.

10\. Invalid TLS certificates are not silently accepted.

11\. A user connects to MinIO through CodeLogic.StorageS3.

12\. The same Connection Manager profile is used for browsing and sync.

13\. A user creates a nightly local-to-S3 sync profile.

14\. The sync service executes it without the desktop UI running.

15\. A preview shows uploads, updates, conflicts, and deletions.

16\. Mass-deletion protection prevents an unsafe mirror operation.

17\. The machine reboots during a transfer or sync.

18\. The service recovers persistent state safely.

19\. A user performs an S3-to-SFTP transfer through a bounded stream.

20\. The app does not load the whole object into memory.

21\. A connection password never appears in logs or diagnostic exports.

22\. Core provider and sync projects build without WinForms dependencies.

23\. A future Linux UI can reuse the provider, transfer, and sync layers.

24\. Every unsupported provider operation produces an explicit result.

25\. All shutdown paths stop CodeLogic libraries and background workers

&#x20;   gracefully.

21\. QUALITY RULES

============================================================



\- Use modern async C#.

\- Pass CancellationToken through all I/O operations.

\- Prefer immutable operation plans and strongly typed result objects.

\- Expected failures should return structured results where appropriate.

\- Unexpected failures should preserve diagnostic context without secrets.

\- Avoid global mutable state except where the verified CodeLogic design

&#x20; intentionally provides a lifecycle facade.

\- Keep files and classes focused.

\- Keep protocol-specific logic inside providers.

\- Keep WinForms logic out of the core.

\- Do not overengineer a distributed microservice system.

\- Do not implement two-way sync with timestamps alone.

\- Do not store credentials in CodeLogic config.

\- Do not conflate FTP, FTPS, and SFTP.

\- Do not fake cross-platform WinForms support.

\- Do not default to insecure trust settings.

\- Do not generate code until the design is approved.

\- Clearly flag any requirement that the researched libraries cannot meet.

\- Prefer a smaller reliable first release over a huge unreliable release.
